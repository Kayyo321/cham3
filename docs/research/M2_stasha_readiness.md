Historical, superseded for implementation on 2026-10-12: the owner requested a memory-safe compiled language and removal of Stasha. Use the [Rust research](M2_rust_readiness.md) and current M2 task; the findings/receipts below describe the earlier assignment only.

Research date: 2026-10-12. Research/task-preparation baseline: `aa843f7ac19398f580f3577ba047300971ba6095`. Product authority: `PROJECT.md` and approved ADR 0001. This is a feasibility assessment and implementation input, not M2 verification or approval of unresolved designs.

## Recommendation and owner constraint

The owner requires the M2 core in Stasha and explicitly requested Stasha as a submodule. Use `toolchains/stasha`, upstream `https://github.com/Kayyo321/stasha.git`, pinned to `5ada5de229df1255cd9b64ab0e28e94ae3d754b1` (source reports `0.2.0-dev`, ABI 11). Its LLVM gitlink is `348061d58dfe5e59027a0d6d51f916197cdd8d68` (LLVM/Clang `23.0.0git`). Do not substitute the similarly named local installation or follow a moving upstream branch.

Stasha appears suitable for a bounded hosted GNU/Linux implementation, subject to M2-specific qualification. Keep contract schema interpretation, authorization/key-class rules, ECR graph validation and transaction state machines, lifecycle rules, and recovery orchestration in `.sts`. Native libraries may perform cryptographic primitives and OS/database operations through narrow scalar/pointer interfaces. Thin bindings cannot become a second C implementation of cham3 policy or ECR semantics. This recommendation does not claim general memory safety or a complete standard library.

## Candidate native dependencies — design decisions still required

| Candidate | Why it fits / work still needed |
|---|---|
| Debian libsodium | [Ed25519 detached signing/verification](https://doc.libsodium.org/public-key_cryptography/public-key_signatures), [explicit Argon2id KDF selection](https://doc.libsodium.org/password_hashing/default_phf), [XChaCha20-Poly1305](https://doc.libsodium.org/secret-key_cryptography/aead/chacha20-poly1305/xchacha20-poly1305_construction), SHA-256 and Linux random source can cover the mandated primitives. Use ordinary Ed25519 for the COSE signing structure, not Ed25519ph. Store explicit Argon2id algorithm/version and calibrated parameters; a library's default can change. Test real provider calls, error returns and all binary lengths. |
| Guarded provider memory | [libsodium memory guidance](https://libsodium.gitbook.io/doc/memory_management.md) supplies wipe, guarded allocation and lock calls. Successful allocation is not proof memory was locked; check required protections explicitly. Handle allocator pairing, no hidden secret copies, core/ptrace restrictions and cleanup. No implementation can claim protection against a compromised kernel. |
| libcbor / reviewed COSE handling | [libcbor](https://libcbor.readthedocs.io/en/latest/) is a maintained codec candidate; its current online docs need version checking against Debian. Stasha owns the fixed schema and deterministic-profile checks. [RFC 8949 §4.2](https://www.rfc-editor.org/rfc/rfc8949.html#section-4.2) and [RFC 9052 §§4.2–4.4](https://www.rfc-editor.org/rfc/rfc9052.html#section-4.2) govern bytes and signing structure. Parser acceptance is not proof of canonical encoding; bound parsing before allocation and reject duplicate/noncanonical data. Review a maintained COSE library candidate versus a narrow standards-based envelope adapter; neither choice is frozen here. |
| SQLite / another durable backend | [SQLite atomicity](https://www.sqlite.org/atomiccommit.html) and [durability settings](https://www.sqlite.org/pragma.html#pragma_synchronous) make SQLite a plausible objects/index transaction backend. A successful database commit is not a rollback-resistant anchor; a second file on the same restorable disk is not independent freshness proof. Model backup/tail/index rollback and actual storage assumptions before choosing. |

Debian's primary package pages list amd64 development packages for [libsodium](https://packages.debian.org/trixie/libsodium-dev), [libcbor](https://packages.debian.org/trixie/libcbor-dev), and [SQLite](https://packages.debian.org/trixie/libsqlite3-dev). Observed versions were `1.0.18-1+deb13u1`, `0.10.2-2`, and `3.46.1-7+deb13u2` respectively. This web snapshot is availability evidence only; capture actual signed APT inputs/versions in the disposable Debian build and do not assume newer online APIs exist in those packages.

## Required feasibility gates

1. Build/qualify the pinned compiler and runtimes on a disposable Debian 13 amd64 environment; record source/submodule/toolchain/runtime/compiler hashes and exact build inputs. Upstream Ubuntu PASS cannot waive this.
2. Compile and execute real Stasha-to-provider probes for Ed25519, Argon2id, XChaCha20-Poly1305, SHA-256, random failure, guarded memory, bounded CBOR, durable database transactions and the selected credential-aware IPC. Include negative results, ownership/ABI/error cleanup and O0/O2 comparison. Provider choices remain subject to design approval.
3. Prove the test runner executes a newly built binary, counts tests, and fails on deliberate compile/link/assertion failures and zero tests; stale output must never become evidence.
4. Freeze reviewed wire, service, lifecycle, storage/anchor, privacy, authentication and identity designs as required by ADR 0001 before dependent backend implementation.
5. If a necessary Stasha feature fails, record a minimal reproduction and gated upstream change/revised pin. Do not silently replace the core with C or change the user's separate dirty language checkout.
