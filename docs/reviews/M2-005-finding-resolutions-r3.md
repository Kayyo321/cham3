## Resolution matrix

| ID | Resolution | Changes | Verification |
|---|---|---|---|
| R2-01 (Medium) — failed creation-directory syncs forgotten across restart and replay | The existence of a directory entry is never taken as proof that an earlier sync of it succeeded. `journal_store_t::open` syncs `root` in its parent and `users` in `root` on **every** start, whether or not this start created them (a start whose sync failed refuses the store and leaves the directory visible; the next start repeats the sync before anything is acknowledged). `open_journal`, which every replayed user goes through at start, syncs the user directory on **every** open: the sync that followed the journal's creation, or a recreated reserve's, may have failed before a restart; a user whose sync fails at start is unusable for that run. `create_journal` keeps syncing `users` on every attempt. The cost is bounded: three directory fsyncs per start plus one per user. The `<uid>` entry in `users` needs no start-time sync: a journal exists only after the `users` sync of the same `create_journal` call returned success (the sync precedes the reserve and the journal), and a user directory without a journal is no user (decision 2). | `registryd/src/journal.rs` (`open`, `open_journal`, module documentation) | **Rust tests** `a_failed_startup_directory_sync_is_repeated_at_the_next_start` (a new root whose parent sync fails: the store is refused, the directory is visible, the next start syncs parent and root before the enrollment; an existing root whose `users` sync fails: the same) and `a_failed_creation_sync_is_repeated_when_the_journal_is_reopened` (the journal written and its directory sync failed: the next start syncs `users/1001` before it replays and acknowledges the enrollment as already present; a reserve recreated at start whose directory sync fails: the user is unusable, the next start syncs the directory again, the first certificate refills the reserve). `every_created_directory_entry_is_durable_before_the_enrollment_is_acknowledged` now asserts the exact syncs of a reopened store (parent, root, each user directory); `a_failed_parent_directory_sync_is_repeated_before_a_retry_is_acknowledged` the exact syncs including the start.<br>**Seeded defects** `store_open_trusts_existing_directories` (the revision-2 conditional syncs) and `reopened_user_directory_not_synced` are each detected; `new_users_directory_not_synced_in_root` re-anchored.<br>**Reviewer's tests** `edge_failed_root_parent_sync_survives_restart`, `edge_failed_users_parent_sync_survives_restart`, `edge_directory_journal_creation_sync_failure_then_restart`, `edge_directory_recreated_reserve_sync_failure_then_restart` pass; `edge_failed_uid_sync_restart_and_two_users` still passes (exactly two `users` syncs for two enrollments after a restart). |
| R2-02 (Low) — a full reserve length bypassed the retry of a failed reserve sync | The reserve's durable size (`reserve_bytes`) is tracked separately from the file's length and is never read off it. `create_journal` calls `allocate` on every attempt, also for a reserve that already has its full length (the allocation then writes nothing and syncs), so a creation retry after a failed sync fails again until a sync succeeds. `replenish_reserve` continues the allocation from the file's actual length, and counts the reserve as full only when the allocation — including its sync — returns success and the file is full; any failure leaves the reserve pending (restrictive records unaffected, the next non-restrictive append tries again).
