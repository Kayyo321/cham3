## Not changed, and carried forward

- **M2-006 restriction ledger (R01):** a pending denial lives in identityd's memory. In M2-004 the vault's durable pending bundle retries the invalidation, and every vault operation of the user completes it first, so the vault does not sign for that user until the invalidation is durable. Other services resolving the key between an identityd restart and that retry see only the durable state. Holding a not-yet-durable restriction across a restart is the restriction ledger's job (service IPC `restrict`: in-memory denial, restriction-ledger entry, durable record).
- **M2-006/M2-007 serialization (R03):** the second check narrows, but does not eliminate, the window in which another service's restriction can cross a signature. Linearizing restrictions with signatures across the real services remains an integration obligation.
- **M2-005 (R04):** proposal ids are kept in vaultd's memory with the pending proposals, so a vault restart drops both. Admission must still reject duplicate request ids independently.
- **M2-006:** named-key restoration, cleanup of other named keys and deletion with real registry and anchor tests (the review's recorded scope).
