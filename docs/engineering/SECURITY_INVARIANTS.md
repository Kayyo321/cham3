# cham3 Security Invariants

Source: `PROJECT.md`. These are approved requirements at the specification level; this file does not assert they are implemented. Tests and current evidence are tracked separately in `docs/STATUS.md`. “Proposed” recommendations must be recorded in an ADR and are not requirements until approved.

| ID | Required behavior | Enforcement boundary | Failure behavior | Verification | Reference |
|---|---|---|---|---|---|
| SEC-01 | Applications receive no ambient authority; access is explicitly provisioned. | Launcher, kernel controls, brokers | Deny unavailable/unapproved resource | Attempt access to ungranted files, devices, IPC and network | PROJECT §3.2, §18 |
| SEC-02 | Same-user applications have distinct security contexts and cannot access one another's protected resources. | Application identity/runtime, filesystem/process controls | Deny cross-app access | Two-app isolation tests, including child processes | §2.2, §6, §15 |
| SEC-03 | A signature authenticates bytes and issuer; current authorization is separately checked. | Contract verifier, key registry, policy evaluator | Reject malformed, unauthenticated, expired, revoked, wrong-scope or disallowed-authority grants | Tamper, key substitution, authority, expiry and revocation tests | §4–5, §15.1 |
| SEC-04 | Contract changes create immutable signed revisions; stale revisions cannot restore authority. | Registry and policy epoch | Reject superseded state | Revision rollback and replay tests | §5.4, §15.1 |
| SEC-05 | Apps cannot access private signing keys or arbitrary signing operations. | Vault API, OS identity and authorization path | Reject app-originated or unapproved signing | Direct API and confused-deputy tests | §4.3–4.6, §14 |
| SEC-06 | Effective policy respects mandatory restrictions above user grants. | Policy evaluator and kernel/broker enforcement | More restrictive policy wins; deny on uncertainty | Conflicting policy tests | §3.2–3.3 |
| SEC-07 | Missing/invalid network authorization starts Offline; Offline has no external path. | Namespace, firewall, host-service boundary | Deny external traffic | IPv4/IPv6, DNS, proxy/IPC bypass tests with positive controls | §3.2, §8, §15.3 |
| SEC-08 | Tor traffic cannot fall back to direct routing; unsupported traffic is denied. | Network namespace, gateway, nftables and DNS path | Quarantine/block on gateway or enforcement failure | Packet observation during normal, failure, restart and reload | §8, §15.3, §18 |
| SEC-09 | Direct mode follows configured policy; it carries no anonymity guarantee. | Per-app network backend | Apply configured constraints; no claim of anonymity | Observe routing and verify policy boundaries | §8 |
| SEC-10 | Child processes do not gain more authority than their application context. | Launcher, credentials, namespaces and process controls | Inherit or reduce authority | Fork/exec/helper-process tests | §6, §15.2 |
| SEC-11 | Window identity shown by KDE is verified; UI state never asserts enforcement by itself. | Trusted attribution service and enforcement status API | Show unknown/denied state; do not authorize from title alone | Spoofed window, wrong process and unenforced contract tests | §2.5, §9, §15.4 |
| SEC-12 | Permission expansion requires appropriate authenticated user authorization; inspection alone is not authorization. | Trusted UI, authorization service and vault | Cancel/reject leaves prior effective policy | Approval, cancel and authorization tests | §4.6, §9, §15.4 |
| SEC-13 | Network transitions and enforcement failures remain fail closed; existing connections are handled per approved transition. | Supervisor, network backend, launcher | Quarantine and deny until enforcement confirmed | Transition, socket teardown, crash, restart and rollback tests | §8, §15.3, §16 Phase 6 |
| SEC-14 | Revocation blocks subsequent mediated access; limits for already copied data and open resources are stated honestly. | Registry, brokers, runtime controls | Deny future use; terminate revocable active access as specified | Resource-specific revocation tests | §5.5, §15 |
| SEC-15 | Cross-user contracts and signing authorities cannot be reused. | User-bound key registry, issuer and resource checks | Reject | Cross-user substitution tests | §3.1, §4, §15.1 |
| SEC-16 | Privileged services expose only authenticated, narrow operations. | Service credentials, IPC authorization, service sandbox | Reject unauthenticated/out-of-scope calls | Unauthorized caller and privilege boundary tests | §14–15 |
| SEC-17 | Update/release trust and signing credentials remain separated from ordinary coding and user contract keys. | Build/release pipeline, key custody | No release on failed verification; no PR access to production key | Pipeline permissions and signature verification review | §2.1, §13, §16 Phase 9 |
| SEC-18 | Security claims respect stated threat model: kernel compromise and traffic correlation are not defeated guarantees. | Documentation, design review, tests | Qualify claims and disclose limits | Review claims against PROJECT §3.4 | §3.4, §18 |

The cryptographic suite, contract fields, application identity, resource classes, and transition behavior must follow `PROJECT.md`. Where runtime details remain unspecified, record an owner decision instead of inventing a guarantee. Virtualization is optional only as described in the approved specification; it is not a substitute for required per-application enforcement.
